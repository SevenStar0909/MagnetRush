# プレイヤー実装仕様（α追加分）

対象機能: **スタブ攻撃 / ジャンプ / 被弾アニメーション / 空中アニメーション**

実装者は他メンバー。本書は「**何をする機能か**」と「**プロジェクトとして守るべき設計ルール**」を提示する。具体的なクラス名・フィールド名・コード差分は実装者が既存コードを読んで決める。

---

## 0. 前提として守るべきルール

### 0.1 アーキテクチャ分担

プレイヤーは責務ごとに分離されている。新機能も同じ分離を踏襲すること。

| 責務 | 既存の例 | 担当する内容 |
|---|---|---|
| **Controller** | `AimController` / `ShootingController` / `PoleController` | 入力消費・能力ロジック。`Player` は持つだけで実処理は Controller |
| **State** | `IdlePlayerState` / `MovePlayerState` / `AimPlayerState` / `DiePlayerState` | 「その状態の間はこういう挙動」「他状態への遷移条件」を持つ。FSM 駆動 |
| **Animator 駆動** | `PlayerAnimator` | Animator パラメータの送出はここに**集約**。他クラスから `animator.Set〜` を呼ばない |
| **イベントハブ** | `PlayerEvents` | UnityEvent 中継。VFX/SFX/UI 等の他システムが購読する |
| **入力ハンドラ** | `PlayerInputHandler` | 入力受信・バッファ管理。Controller/State から peek/consume される |
| **設定** | `PlayerSettings` (SO) | 全パラメータは SO 外出し。Inspector / コードでハードコード禁止 |

新機能を作る時の判断基準:

- 「能動的な行動・能力」（プレイヤー操作で発火するもの）→ **基本は Controller + State の両方を作る**。既存のエイム（`AimController` + `AimPlayerState`）がそのパターン
  - **Controller** が入力消費・発動条件判定・SO 値読み取り・State 遷移の起動を担当
  - **State** が発動中の挙動（他入力との排他関係、タイムアウト、Animator 駆動連携）を担当
- 「アニメーションだけで完結する受動的演出」（被弾モーション・空中モーション等）→ Controller / State は不要、`PlayerAnimator` 側で Animator 駆動だけ実装
- どちらか迷ったら既存の `AimController` + `AimPlayerState` の責務分担を読んで真似る

### 0.2 共通禁止事項（プロジェクトルール）

以下は `.claude/rules/` 配下のルールで規定済みなので、違反を避ける:

- **`OnTriggerEnter` 等で `CompareTag` / `layer ==` で陣営判定しない** → Layer Matrix で済ませる
- **Hurtbox は Trigger、Hitbox（攻撃判定）も Trigger、EntityBody は Collider** → `collision-design-principles.md` 参照
- **Animator 操作は `PlayerAnimator` 一箇所に集約** → 他クラスから直接 `SetBool`/`SetTrigger` 禁止
- **パラメータは `PlayerSettings` 経由** → コードに数値ハードコード禁止、Inspector 直書き禁止
- **早期 return ガードは `ChannelLogger.LogGuardReturn` で理由ログを必ず出す**
- **`ForceMode.Force` は使わない** → `VelocityChange` 系（スリープ中の Rigidbody に Force は効かない）
- **コメント・命名は `.claude/rules/comment-guidelines.md` / `naming-conventions.md` に従う**

### 0.3 既存の連動の壊し方を避ける

`PlayerAnimator` には Animator パラメータ・State の登録漏れ検出機構が入っている（`ValidateAnimatorParameters` / `ValidateStateOrder`）。新規追加時はこの検証に引っかからないよう、**「Animator Controller 側」と「コード側」と「FSM 側」を全て揃える**ことを意識する（どれかが欠けると Play 開始時に LogError）。

## 1. スタブ攻撃

### 1.1 機能要件

α仕様書（プレイヤーシート / ボスキャラシート）より:

- 入力: **RB（右ショルダー）**
- 発動条件:
  - **ボスがスタン状態である**
  - **プレイヤーがボスに近接している**（接近判定の距離はチューニング前提で SO 化）
  - 上記2条件が揃った時のみ画面UIに RB プロンプトが出る（UIメンバーが担当）
- 発動時の挙動:
  - プレイヤーは攻撃モーション再生
  - **モーション中は移動・射撃・エイム・ジャンプの入力を受け付けない**
  - ヒット時に**ボスのHPアイコンを1減らす**
  - **ボスのスタン値を 0 にリセットする**
  - モーション終了で通常状態（Move/Idle）に復帰
- スタン状態でないボス、距離外のボスにはRBで発動しない（入力を消費せず無視）

### 1.2 設計ルール

**Controller + State の両方を作る**（既存の `AimController` + `AimPlayerState` 同パターン）。

- **Controller の責務**:
  - RB 入力の peek / consume
  - 発動条件判定（ボススタン中 + 接近距離内）。条件外なら入力を消費せず無視
  - 発動時に State 遷移を起動 + Animator 駆動側へのトリガ通知
  - SO 値（接近判定距離・タイムアウト等）の読み取り
- **State の責務**:
  - スタブ発動中の「他入力ロック」（移動・射撃・エイム・ジャンプを止める）
  - AnimEvent 経由でのヒット通知の受け取り
  - モーション終了時の通常 State 復帰
  - AnimEvent 配線漏れ対策のタイムアウトで強制復帰
- **入力は `PlayerInputHandler` を拡張**。既存の `Is〇〇Pressed` / `Consume〇〇()` パターンに合わせる
- **ヒット判定はボス側のインターフェース**を経由する（プレイヤー側はボスの内部実装を知らない）。スタブを「受ける側」のインターフェースをボスチームに用意してもらい、プレイヤー側はそれを叩くだけ
- **AnimEvent でヒットタイミングを取る**（ボスの腕Hitboxと同じパターン）。Exit Time のみに依存しない
- **イベント発火**: スタブ命中時は `PlayerEvents` 経由で発火する（VFX/SFX/カメラチームのフック先）

### 1.3 ボスチームとの連携

- スタブを「受ける側」のインターフェース設計はボス担当と合意してから実装する
- ボスのスタン状態判定は**ボス側のAPIで取得**（プレイヤー側がボスの内部状態に直接アクセスしない）

### 1.4 受け入れ基準

- [ ] ボススタン中＋接近時のみ発動する。それ以外で RB を押しても何も起きない
- [ ] スタブモーション中に他の入力（移動・射撃・エイム・ジャンプ）が無視される
- [ ] スタブヒットでボスHP -1、ボススタン値 0 にリセット
- [ ] AnimEvent 配線が漏れてもタイムアウトで復帰する
- [ ] スタブヒットの瞬間に PlayerEvents が発火する（他チームが SFX/VFX を載せられる）

## 2. ジャンプ

### 2.1 機能要件

α仕様書には記載なし。プロト段階での想定:

- 入力: **Aボタン**
- 発動条件: **接地中のみ**。空中ジャンプ・二段ジャンプは α では実装しない
- 挙動: 上方向に初速を与えて飛ぶ
- ジャンプ中も**エイム・射撃は可能**
- ジャンプ中の落下・着地は既存の `Entity` 基底の重力・接地処理に任せる

### 2.2 設計ルール

**Controller + State の両方を作る**（既存の `AimController` + `AimPlayerState` 同パターン）。

- **Controller の責務**:
  - A ボタン入力の peek / consume
  - 発動条件判定（接地中のみ）。空中で押されたら入力を消費せず無視
  - 発動時に上方向初速を Rigidbody に付与（`VelocityChange` 系）+ State 遷移を起動
  - SO 値（初速）の読み取り
- **State の責務**:
  - 滞空中であることを FSM 上で明示する（Animator の State Int / 空中アニメ駆動と整合させるため）
  - ジャンプ State 中も**エイム・射撃の Controller 呼び出しは許可する**（既存通り Controller は `Player.Update` で State 横断で走る前提）
  - 接地復帰で通常 State へ戻る
- **接地判定は既存の `Entity.IsGrounded` を使う**。新規 Raycast を書かない
- **重力・落下は `Entity` 基底に任せる**。ジャンプ機能側で重力を再実装しない
- **`ForceMode.Force` は使わない**（スリープ中の Rigidbody に Force は効かない）

### 2.3 受け入れ基準

- [ ] 接地中のみジャンプ可能。空中で A を押しても何も起きない
- [ ] ジャンプ中もエイム・射撃が可能
- [ ] 着地後は即次のジャンプができる（クールダウンなし、ただし接地必須）
- [ ] 初速は SO で調整できる

## 3. 被弾アニメーション

### 3.1 機能要件

- トリガ: **プレイヤーがダメージを受けた時**（死亡には至らないダメージも含む）
- 挙動: 被弾モーションが**短時間**再生される
- **入力ロックはしない**（α版ではプレイヤー操作は止めない方針）
- 死亡時は被弾アニメではなく死亡演出が優先される

### 3.2 設計ルール

- **State 遷移はしない**（操作中断を避けるため）。Move/Aim 中の被弾でも State は変えない
- **Animator のレイヤー分離 or Trigger による短時間遷移**で表現する。実装者が Animator Controller の構成を決める
- **トリガは `Health` のダメージイベント経由**で `PlayerAnimator` が受け取る。`PlayerAnimator` から Animator にトリガを送る（Animator 操作の集約原則）
- **死亡時の優先**: `DiePlayerState` への遷移（既存）が走った場合、被弾アニメは流さない。Animator 側で AnyState 遷移条件に State Int を含めて競合を避ける

### 3.3 受け入れ基準

- [ ] 被弾時に被弾モーションが再生される
- [ ] 被弾中もプレイヤー操作（移動・エイム・射撃・ジャンプ）が可能
- [ ] HP=0 の被弾時は死亡演出が優先され、被弾アニメは流れない

## 4. 空中アニメーション

### 4.1 機能要件

- プレイヤーが**接地していない間**は空中用モーション（上昇 / 下降 / 着地）が再生される
- ジャンプ経由でも、段差落下経由でも、**接地フラグが false なら空中扱い**
- 接地復帰時は短い着地モーションを経由してから通常状態に戻る

### 4.2 設計ルール

- **Controller / State は作らない**。空中アニメは「ジャンプ State or 通常 State + 接地フラグ false」から派生する**演出**であって、能動的な行動ではない
- **Animator 側で `IsGrounded` Bool と垂直方向速度の Float を見て、サブステートマシンで上昇/下降/着地を切り替える**
- **垂直速度は新規 Animator パラメータ（Float）として `PlayerAnimator` から送出する**。`Entity.velocity.y` 相当をそのまま流せばよい
- 新規パラメータを追加したら **`PlayerAnimator` の検証配列にも必ず追加する**（`ValidateAnimatorParameters` で漏れを検出するため）
- ジャンプ State が走っている時も、段差落下で通常 State のまま空中になっている時も、両方で正しく空中モーションが流れること

### 4.3 受け入れ基準

- [ ] ジャンプ直後 → 上昇モーション、頂点超え → 下降モーション、接地 → 着地経由で通常モーションに戻る
- [ ] 段差落下（ジャンプ未経由）でも下降モーションに入る
- [ ] エイム中の落下・着地でもエイム姿勢が維持される（Layer 構成で実現）

## 5. 提出単位の推奨

機能ごとに別 PR にする（レビュー粒度・ロールバック容易性のため）:

| 順序 | 機能 | 想定ブロッキング |
|---|---|---|
| 1 | ジャンプ | なし |
| 2 | 空中アニメーション | ジャンプ完了後（ジャンプで空中状態が発生してから組み込むほうが検証が楽） |
| 3 | 被弾アニメーション | なし |
| 4 | スタブ攻撃 | ボスチームと「受ける側」インターフェース合意後 |

スタブ攻撃が一番後ろなのは**ボスチーム待ち**になる可能性があるため。ジャンプ・空中・被弾を先に終わらせて、スタブはボス側 API が決まり次第着手するのが詰まらない。

## 6. プランナー確認待ち項目

実装着手前に西川（プランナー）に確認:

- ジャンプ初速・滞空時間（α仕様書未記載のため値が無い）
- スタブ攻撃のモーション尺・カメラ演出（カットイン or そのまま）
- 被弾時の入力ロックポリシー（本書では「ロックしない」前提だが、プレイ感次第で再判断）
- 空中アニメーションのレイヤー構成（エイム中の空中挙動：エイム姿勢を保つか、空中専用に切り替えるか）
- スタブ攻撃の「ボス側受ける側」インターフェース仕様（ボスチームと合意必要）

- 命名・コメント規約で迷ったら → `.claude/rules/naming-conventions.md` / `comment-guidelines.md` 参照
